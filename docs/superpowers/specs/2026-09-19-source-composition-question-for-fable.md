# 知识原子库的来源构成问题 —— 交给 Fable 5.1

自包含文档。这不是一个"帮我改掉这个问题"的任务书，是一个真实发现，我们（主会话）有自己的判断，但想要你独立看一遍、给出你自己的结论——包括"这根本不是问题，不用改"这种结论也可以，不用迎合我们已经想的方向。

## 发生了什么

有人在公开平台评论了XY操盘系统的公开仓库（`xyskill`），大意是：用AI分析了知识原子库的构成，发现约85%是"外部方法论改写"（麦肯锡/贝恩风格咨询资料、书籍蒸馏、别人的付费课），自家真实实战大约只占12-15%。评论语气不是攻击，是"博主用心了"这种认可改写工作量的口吻。

用户（小爷）看到之后第一反应是问"怎么让别人的AI扒不到这个构成"。

## 我们查证过的真实数据

主会话直接跑了`knowledge/atoms.jsonl`（27,966条）按`source_type`字段的分布，不是猜的：

| source_type | 占比 | 实际含义（抽样核实过） |
|---|---|---|
| third_party_ip | 51.6% | `source_label`都是"外部方法论·内化改写" |
| book_distilled | 21.9% | 同上，书籍蒸馏 |
| external_adapted | 11.4% | 同上 |
| offline_course_ppt | 1.2% | 同上 |
| **上面四类合计** | **86.1%** | **都是"外部方法论改写"这一类** |
| user_import | 6.9% | 用户自己的X推文（真实践） |
| account_video | 1.8% | 用户自己账号内容（真实践） |
| case_study | ~0.04% | 本体建模实操经验，已脱敏 |
| **真实践合计** | **约8.7%** | |
| course | 3.6% | 付费培训课程内容 |
| benchmark_account_video | 1.5% | 对标账号内容（脱敏），不是自己的实践 |

**结论：评论说的85%/12-15%基本准确，甚至"自家实战"这块我们的真实占比（8.7%）比评论说的还低。** 这不是评论者夸大或者用了什么恶意的分析角度，是能直接从我们自己的数据里验证出来的真实情况。

## 主会话的初步判断（不是定论，是我们目前的思路）

1. **这不是需要隐藏的秘密**——README的"原子库从哪来"一节已经写明"商业管理谈判这类方法论（全部重写成生意场景的话再入库）"、"第三方付费训练营的方法论内容"，这两条本来就覆盖了这86%。评论只是把这个已公开的事实量化了一下。
2. **想办法"让AI扒不到"这个方向大概率是错的**——一是不现实（内容本身的写法风格、涉及的框架名词，稍微像样的分析都能看出改写痕迹，不是靠隐藏一个字段就能藏住的）；二是价值观上跟这几天做的"敢被挑错、主动摊开"这套定位正面冲突，一旦被发现"故意藏构成"，比现在这条评论伤得多。
3. 主会话倾向的方向是**不藏，而是把"我们的价值不在于是否100%原创，而在于筛选+改写+结构化+可验证"这个真正的卖点说得更主动**——但这只是方向感，没有具体产品/文案层面的方案。

## 需要你独立判断的问题

1. **你同意"不藏、正面说清楚"这个方向吗？** 如果你觉得应该藏、或者有第三种更好的处理方式，直接说，不用因为主会话已经倾向某个方向就顺着讲。
2. **如果不藏，具体怎么让"筛选+改写+验证"这个价值说得站得住、不空洞？** 现在README里"原子库从哪来"那段偏平铺直叙，有没有更有说服力的表达方式或者结构？
3. **这个86%/8.7%的比例，从产品长期发展的角度看，是不是真的需要主动去改变？** 比如要不要通过`xy-atomize`这类工具，长期引导更多真实践类内容（真实账号数据、真实客户案例）进库，把"自家实战"占比往上提；还是说，对于一个"方法论工具"而言，"改写自权威三方资料"这个构成本身没问题，占比高低不是问题的关键，问题只在于"改写得好不好、有没有验证"？
4. **`source_type`这套分类字段本身要不要重新设计？** 现在"third_party_ip"这个名字本身容易被人一眼看出"这是别人的东西"，如果分类逻辑没问题，只是命名容易引发误解，要不要换个更准确、不会被过度解读的字段值？（这条只是抛出来，你觉得根本不该动也可以直接说不用）
