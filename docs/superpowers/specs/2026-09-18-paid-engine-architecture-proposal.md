# 付费引擎架构提案（回应 2026-09-18 设计任务书）

> 提案，不是终稿。写给 XY 主会话做可行性核对用。每一节先给判断，再给理由，最后给"可以直接反驳我的点"。
> 依据：`ontology-schema.md`、`concepts-schema.md`、`xy-atomize/SKILL.md`、`xy-fde/SKILL.md`、`scripts/atoms-search.py`、`scripts/ontology-lint.py`、`scripts/concepts-stage-funnel.py`、两份 HANDOFF 及其执行结果（309 节点、23,812 条改标）。

## 0. 先纠正一个前提：引擎今天到底是什么

任务书把付费产品描述为"方法论工具"，但要先说清楚这个"工具"的真实形态，否则四个问题都会答偏：

| 部件 | 现状 | 形态 |
|---|---|---|
| 阶段 0–5 流水线 | `concepts-schema.md` 里全部标"脚本（待写）" | **不是脚本**。实际由 Claude Code 会话读原子、做判断、写 jsonl 完成（两份 HANDOFF 就是这么跑的） |
| 校验 | `ontology-lint.py` | 真代码，零依赖，只读 |
| 检索 | `atoms-search.py` | 真代码，默认打云端 `api.xyskill.xyz`，失败回退本地 |
| 粗筛 | `concepts-stage-funnel.py` | 真代码，已被实测降级为"决定比对谁"，不再是过滤器 |
| 判断规则 | 散在 schema、HANDOFF、SKILL.md 里 | **markdown 文本**，运行时由客户的模型读取执行 |

结论：**引擎的可执行核心是"校验器 + 流程闸门 + 校准数据"，判断本身外包给客户自己的模型。** 这不是缺陷，是零依赖路线的必然结果，而且它决定了两件事：

1. 任何"把判断规则藏起来"的方案在 Claude Code 形态下都不成立——规则必须被模型读到才能执行，客户的会话记录里全部可见。护城河不能建在 prompt 保密上（详见第 4 节）。
2. 判断质量随客户的模型而变（Claude Code 里客户用什么模型、什么额度，XY 管不了）。所以引擎必须自带"判断质量校准"环节，否则同一套工具在不同客户手里产出差异极大，XY 无法对结果负责（详见第 5 节）。

## 1. 交付形态：闸门式流水线 + 三档服务（问题 1）

### 判断

不选 A、B，也不是空泛的"混合"。推荐 **"闸门式流水线"（gated pipeline）**：工具把六步法跑成一条有固定停靠点的流水线，每个停靠点产出一份**闸门包**（gate packet）——一个小而结构化的文件，装着"这一步的规则提案 + 抽样 + 待人拍板的问题"。三档服务只在"谁来看闸门包"上区分，工具本身完全一样：

| 档 | 谁审闸门包 | 卖的是什么 | 对应任务书选项 |
|---|---|---|---|
| 自助档 | 客户自己（模型给建议，人点头） | skill + 校验器 + 校准套件 + 规则包更新 | A |
| 审核档 | 客户跑，闸门包发 XY，XY 异步回批 | 每个闸门一次判断，按闸门数计价，不按小时 | C 的可执行版 |
| 驻场档 | XY 亲自跑全流程 | 时间 + 判断 + 组织推进 | B |

### 闸门从哪来：不是设计出来的，是试点里已经出现过的停顿

两天实操里真正需要人拍板的地方，就是闸门。逐一对应：

| 闸门 | 试点里对应的真实事件 | 闸门包内容 | 自助档能否自过 |
|---|---|---|---|
| G0 定边界 | `ontology-schema.md` 的"边界声明"（管什么、明确不管什么） | 边界声明草案 + 样本目录扫描（文件数/字数/格式） | 能 |
| G1 抽取规则定型 | `xy-atomize` Phase 1"抽 3 篇过用户确认再批量" | 3 篇样本的原子 + 拆分/脱敏/type 判断规则草案 | 能，但必须人点头 |
| G2 批次数据质量规则 | 63.3% 错标发现；"每个新批次都要独立抽样，不能泛化套用"的教训 | 该批次前缀/来源分布 + 30 条抽样 + 规则提案（比如"XY-CE 前缀→通用商业管理"） | 能，附抽样 |
| G3 矛盾候选 | `contradicts` 不做自动推断；IPP-031↔XY-DY-053 的人工判定过程 | 同场景/同决策维度的候选对 + 各自证据 + 模型的方向性判断 | **不能自动应用**，只能人审 |
| G4 节点去重与层级 | 阶段 2"宁可留重复不错合并"、possible_parent→refines | 疑似重复对 + 建议（合并/refines/保留） | 能，默认保留 |
| G5 验收 | `ontology-lint.py` 0 违规 + 索引生成 | lint 报告 + concepts-index + 矛盾清单 | 能 |

这个闸门表就是产品规格。工具的工作是**把闸门包做得足够小、足够结构化**，小到审核档的 XY 能在 20 分钟内回批一个，小到金融客户敢脱敏后发出来（第 4 节会用到这一点）。

### 为什么这样能解决 A 和 B 各自的问题

- A 的"非技术客户用不起来"：**不试图解决**。自助档的目标用户就是"已经在用 Claude Code 的团队"，这是真实存在且在增长的人群；非技术客户走审核档或驻场档，不为他们造 GUI。造 GUI 会立刻打破零依赖路线，而且 XY 没有前端维护能力。
- A 的"方法论被看光、被转卖"：**承认看得光，改在别处设防**（第 4 节）。闸门包机制本身就是防转卖的一部分——转卖者拿到 skill，拿不到审核档背后的判断积累。
- B 的"卖时间不可复制"：审核档把 B 里最值钱的部分（判断）切成了**固定尺寸的工件**，按件计价、可异步、可排队、可以由 XY 训练出的第二个人来做，这就从"卖时间"变成了"卖判断件"。
- C 的"怎么混"：**不按"80% 工具 + 20% 人工"分比例，按闸门分**。工具做闸门之间的全部工作，人只出现在闸门上。比例是结果不是设计。

### 两天实操的直接证据

两份 HANDOFF 文档本质上就是两台机器之间的闸门包：一台机器写"已完成/待做/不要直接信这个描述"，另一台机器接手、独立核实、回报"我换掉了你给的配对"。这个异步、结构化、允许接手方推翻的协作模式已经在真实工作里跑通了两轮，审核档就是把它产品化，把"另一台机器"换成"客户"或"XY"。

### 可以直接反驳我的点

- 如果 XY 判断自己 12 个月内根本不会有"已经在用 Claude Code 的企业客户"，自助档就是伪需求，应该只做审核档 + 驻场档，工具退化成 XY 内部提效工具。这个判断我做不了，要看 XY 的客户漏斗。

## 2. 通用企业版：三层分离 + 画像文件（问题 2）

### 判断

把方法论拆成三层，只有第一层是"XY 的"，第二层是"客户的"，第三层是"这次工程里长出来的"。工具的通用性来自**第三层是产物而不是输入**：

| 层 | 内容 | 谁定 | 能否改 |
|---|---|---|---|
| **不变核** | 六步顺序；"一个原子一个判断"；8 个 type 及其语义角色；5 种 rel；概念节点聚合（原子挂节点、节点连节点）；"contradicts 不自动推断"；闸门顺序；lint 硬规则（枚举封闭、无死链、case/number 必须有来源） | XY | 不可配置 |
| **画像**（profile） | topics 枚举；id 前缀方案；source_type 集合；语言；原子长度上限；每个 type 的客户侧别名（比如客户把 anti-pattern 叫"禁令"） | 客户，在 G0/G1 生成 | 可配置，lint 读它 |
| **校准规则**（rules） | 候选节点提取标准、数据质量过滤规则、去重判定口径、矛盾判定的"同场景"定义、few-shot 样例 | 在 G1–G4 闸门上由人拍板后**写回文件** | 每个客户一份，随工程增长 |

### 具体落地形态：一个客户工作区

```
<客户仓库>/
  ontology/
    profile.json          # 画像：topics、id前缀、source_types、语言、type别名
    rules/
      extraction.md       # G1 定型的抽取规则 + 3 篇样本作为 few-shot
      quality.md          # G2 逐批次的数据质量规则（追加式，每批一节）
      dedup.md            # G4 的去重口径 + 已判例
      contradicts.md      # G3 的"同场景"定义 + 已判例
    gates/
      G1-2026-xx-xx.md    # 闸门包归档，审核档时这就是发给 XY 的东西
  knowledge/
    atoms.jsonl
    concepts.jsonl
    concepts_revisions.jsonl
    usage_ledger.jsonl    # 第 3 节
  scripts/                # 从 XY 引擎复制，零依赖
```

### 两个必须改的现状

1. **`ontology-lint.py` 把 14 个 topics 硬编码在 `VALID_TOPICS` 里。** 企业版第一件事就是让 lint 读 `profile.json`。这是通用化唯一真正需要改代码的地方，其余都是流程。
2. **`atoms-search.py` 默认打 `api.xyskill.xyz`。** 企业版必须反过来：默认本地，云端显式开启。否则客户安全审查第一天就会看到脚本对外联网（第 4 节展开）。

### "要不要按行业定制 prompt"——答案是定制的不是 prompt，是判例

私域库和交易系统代码库能用同一套方法跑通，说明**不变核够通用**；两者真正不同的是"什么算一条原子"（一句判断 vs 一个模块的职责陈述）和"什么算同场景"（一转定价 vs 同一事件总线上的两个消费者）。这些差异不该靠 XY 提前给每个行业写一套 prompt——XY 不可能懂所有行业，而且预写的规则会像"XY-CE 前缀"那样在下一个批次失效。

正确做法是 **G1 的 3 篇样本循环**：模型先抽，人改，改法写成规则，规则进 `rules/extraction.md`，后续批次按规则走。这就是 `xy-atomize` 已经在做的事，只是把"规则记在对话里"改成"规则写进文件"。行业定制因此是**每个工程的副产品**，而不是 XY 的前置投入。

### 客户的分类体系：不削足适履，但 topics 也是抽出来的

不要求客户套 XY 的 13 个 topics——那是私域库的分类，对企业没有意义。但也不要让客户"填一份 topics 表"，他们填出来的通常是组织架构图，不是知识分类。做法：把 **topics 本身当作阶段 0 的产物**——先对客户文档做一轮候选提取，让候选节点的聚类反推 topics，人在 G0 上确认。这跟"通用商业管理"topic 的诞生过程是一样的：不是预设，是数据里长出来的。

### 可以直接反驳我的点

- 8 个 type 我坚持不开放。理由是 lint 的每条硬规则都绑在 type 语义上（principle 孤立是警号、number 必须有来源）。开放 type = 放弃校验。但如果真有客户领域需要第 9 个 type（比如代码库里的"接口契约"），允许的做法是**别名映射到 8 个之一**，不是新增。这点如果 XY 实操中发现映射不下去，就是我错了。

## 3. AI Native 自迭代：三种信号、一个合并器、一道人闸（问题 3）

### 判断

"自我迭代"在这套架构里的准确含义是：**提案自动生成，采纳由人决定，人的决定变成新的校准数据。** 不是让系统自己改本体。理由不是保守，是两天里已经验证过的三件事：`contradicts` 自动推断误判率高到必须撤回；文本相似度漏斗在真实数据上失效；"上一批次的规则"套到下一批次会误伤。三次都是"自动应用"出问题，"自动提案 + 人过"没出过问题。

### 三种反馈信号（全部本地落盘，`usage_ledger.jsonl`）

| 信号 | 来源 | 记录什么 | 触发什么提案 |
|---|---|---|---|
| 显式 | 客户在用本体回答业务问题时标"对/错/缺"，或直接投喂一个新案例 | query、命中的 concept/atom id、标记、附带文本 | 错→该节点的证据复核；缺→候选节点；新案例→走抽取入库（现有 `xy-atomize` 路径） |
| 隐式 | 检索日志 | 无命中的 query（覆盖缺口）；总是一起被命中的节点对（疑似应合并或应建 refines）；命中但从未被采纳的节点（疑似摘要失真） | 候选节点 / 去重候选 / 摘要重写候选 |
| 冲突 | 入库时的矛盾判断（`concepts-schema.md` 已设计） | 新原子与所在节点既有证据的方向性冲突 | G3 矛盾候选 |

### 合并器（consolidator）：离线、定期、只产提案

- **绝不在请求路径上跑**（WeKnora 的注释原话，两天里也一直遵守）。
- 触发条件二选一先到：新增原子 ≥ 50 条，或 7 天。
- 输入：ledger 增量 + 当前 concepts + rules。输出：一份 **G6 迭代闸门包**，结构与 G2–G4 完全一致（候选 + 证据 + 模型建议 + 待拍板项）。
- 自动应用白名单，只有两类：① 给已有节点追加证据，且新原子与节点既有证据高度同向（模型判 supports 且人此前对同类判例批过）；② 追加 aliases。**合并、拆分、contradicts、摘要重写，永远走人闸。**
- 每次应用写 `concepts_revisions.jsonl`，`edit_source` 用现有三值（pipeline / llm_judge / human），加一个 `ledger_ref` 指回触发信号，做到"这个改动是哪次客户反馈引起的"可追溯。
- 季度做一次全量重跑（阶段 2/4/5），对照上一版差异，人审后升 ontology 版本号；消费方（客户的各 skill）可以钉住版本，坏了能回退。

### 飞轮在哪

人的每次闸门决定都追加进 `rules/*.md` 作为判例。下一次合并器提案时，模型读到的规则里多了这条判例，同类情况的提案质量就高一点，人要看的东西就少一点。**迭代的驱动力是客户自己的使用和拍板，XY 不需要出现**——这满足任务书对"不靠 XY 人工维护"的硬要求。审核档客户的闸门包会经过 XY，XY 因此能看到"哪类判例在多个客户那里反复出现"，这是 XY 自己的规则包（不变核之外的默认规则）迭代来源，但**只带判例形态，不带客户数据**，且要在合同里写明。

### 可以直接反驳我的点

- 触发阈值（50 条 / 7 天 / 季度）是拍的，没有任何数据支撑。第一个客户跑三个月后再定。
- 隐式信号里"无命中 query"可能大量是客户随手乱问，噪音比例未知，需要先看一个月的 ledger 再决定要不要用它。

## 4. 护城河与数据主权：本地优先，护城河不靠保密（问题 4）

### 判断

"云端授权网关把核心逻辑放服务端"这条路，**建议放弃**，不是因为金融客户用不了，是因为它在 Claude Code 形态下根本保护不了想保护的东西，还会把 XY 变成客户数据的托管方。分三点说：

1. **技术上藏不住。** 判断规则必须进模型上下文才能执行，客户会话记录里全文可见。就算把规则拆成 API 调用（客户端发原子、服务端返回判断），服务端返回的判断本身就是规则的显影，几百次调用就能把规则反推出来。真正能藏的只有"服务端的模型比客户端强"——而这套架构的模型是客户自己的 Claude Code，XY 没有更强的模型可藏。
2. **商业上代价大于收益。** 每个原子都要过 XY 服务器 = XY 托管客户全量业务知识 = 安全审查、合规责任、可用性承诺全部落到 XY 头上，而 XY 是个零依赖脚本团队。金融/医疗客户直接失去，其他客户也会在采购流程里被问"你们的服务器在哪、谁能看"。
3. **现状已经埋了雷。** `atoms-search.py` 默认打 `api.xyskill.xyz`，这在 XY 自己的 skill 里没问题，但企业引擎绝不能沿用——一个"默认联网、失败才本地"的脚本在客户安全审查里是一票否决。企业版默认本地，云端能力显式 opt-in。

### 护城河改建在四样东西上（都不依赖保密）

| 护城河 | 是什么 | 复制者拿不到的原因 |
|---|---|---|
| **校准资产** | 273 条已标注匹配、63.3% 的批次规则、漏斗失效的校准曲线、G3 判例集、回归用例 | 这是数据，不在 prompt 里；抄走 skill 的人没有它，而且它每个客户工程都在增长 |
| **回归套件** | 一组"已知输入 → 应得结果"的用例，随 skill 发布，客户可以自己跑 | 复制的 skill 在下一个模型版本上坏了没人知道；正版有回归能证明还能用 |
| **审核档** | 闸门判断作为服务 | 判断能力来自 XY 看过的判例总量，转卖者从零开始 |
| **签名规则包 + 可追溯** | 规则包按客户签发，带客户标识 | 不是 DRM，挡不住复制，但泄露的包能追到源头，配合合同就够用 |

再加一条最朴素的：**方法论会更新，复制品会冻结。** 两天里规则改了三次（44%→63.3%、漏斗降级、IPP-031 配对换掉），复制者拿到的是某一天的快照。

### 数据主权的具体解法：本地全功能，四个可选出口

引擎**离线全功能**，这是设计前提不是兜底。四个网络出口全部可选、全部可审计、全部可用文件替代：

| 出口 | 默认 | 内容 | 涉密客户替代方案 |
|---|---|---|---|
| 许可校验 | 开 | 本地签名许可文件，带到期日，脚本校验签名，**不联网** | 本来就不联网 |
| 规则包更新 | 关 | 拉取签名后的 `rules` 默认包和回归套件 | 文件拷贝，签名照样校验 |
| 遥测 | 关 | 只有计数（跑了几个闸门、lint 几违规），无文本 | 不开 |
| 闸门包上传（审核档） | 关，逐包确认 | 闸门包本体 | 客户脱敏后自行传递，或 XY 驻场 |

闸门包的设计目标之一就是为这一条服务：它由**规则文本 + 计数 + 客户挑选的少量样本**构成，天然小、天然可脱敏。审核档在涉密客户那里退化为"客户传脱敏包，XY 回批"，仍然成立。

### 可以直接反驳我的点

- 我假设"客户自己的模型"就是运行时。如果 XY 未来真的拥有比客户更强的判断模型（比如用累计判例微调出的专用模型），"服务端判断"才重新有意义。那时护城河变成模型本身，架构要重画。现在没有，不要为不存在的模型设计网关。

## 5. 你们没提但我认为必须放进设计的四件事

### 5.1 判断质量校准是引擎的一部分，不是可选项（最重要）

引擎把判断外包给客户的模型，那么"这个客户的模型 + 这个客户的规则"能不能达到试点质量，是每个工程开工前必须回答的问题。设计一个 **G-1 校准闸门**：开工前用引擎自带的回归套件（XY 的已标注样本，脱敏后随 skill 发布）让客户环境跑一遍，出一份一致率报告。低于阈值就先调规则或换模型，别开工。这份报告同时是审核档/驻场档的报价依据——一致率低的环境，闸门包会更多、更难审。

副作用：回归套件必须存在。今天没有。第 4 节的护城河也压在它上面，所以这是**第一个要建的工件**。

### 5.2 对外产品的"英雄产出"应该是矛盾清单，不是本体文件

客户不关心 `atoms.jsonl`。两天里最能让人一眼看懂价值的东西是"IPP-031 说一转别超 100 元，XY-DY-053 说 880 元筛客更好，条件分别是……"——**你的公司在哪些事上自相矛盾、各自成立的条件是什么**。G3 和 G5 的输出应该直接生成一份 `contradictions-report.md`，这是 demo、是售前、是客户内部汇报材料。本体文件是它的底稿。

### 5.3 已拍板决策里有一条要重看：定位跟自家原子打架

`xy-fde/SKILL.md` 引用 XY-UZB-105："本体论一类复杂技术在外部增长场景（获客/销售/客服）应用价值有限，性价比通常不划算，别为了炫技去接。"这是 XY 自己库里的原子，而付费引擎正是本体论产品。两者不矛盾的唯一解法是**明确把引擎定位在内部知识/运营/合规场景**（"公司里的规则和判断到底是什么、哪里打架"），不进获客/销售场景。如果销售话术往"AI 获客"上靠，会被自家 skill 反驳。建议把这条写进引擎的边界声明。

### 5.4 成本要变成闸门包里的一个数字

试点数据：私域运营 3,616 条原子约 26 万 token，其余 12 个 topic 约 96 万 token。给一个粗估：**每千条原子约 3–7 万 token**（随规则过滤比例波动）。G0 闸门包应该带一行"按你的目录规模，预计消耗 X token / 约 Y 元"，让客户在开工前知道账单量级。这也是自助档和审核档的定价锚。

### 5.5 一个小但会咬人的工件："重塑不照搬"的机器检查

上一份设计文档的问题 3 问过"完全靠人工内化改写，风险敞口多大"。`xy-atomize` 里已经写着 `tools/name_blocklist.txt` 和 `check_no_attribution` "目前还没建"。企业引擎里这条更重要——客户会投喂第三方材料。建议把它做成 lint 的一个可选规则：`profile.json` 里维护来源方名单，lint 对 `knowledge`、`summary`、`rules/*.md` 全文扫，命中即违规。零依赖，一天能写完。
