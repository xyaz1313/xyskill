# 付费引擎设计任务书 — 写给 Fable 5.1

自包含文档，你不需要看过任何之前的对话记录。这是一个**设计任务**，不是审查任务——上一份文档（`2026-09-17-xy-ontology-design.md`，同目录下，建议你也读一遍作为背景）是让你审查一个已经做出的架构简化决定；这一份是让你**从零设计**付费产品的具体工程架构，因为这件事我们（XY这边）自己还没有答案。

**重要：这是设计提案，不是最终方案**。你产出的设计会被带回XY主对话（另一个Claude Code会话）做可行性核实、跟现有代码库现实情况对照、可能还要走一遍正式的brainstorming+writing-plans流程，才会真正开始写代码。所以你可以大胆设计、指出问题、提出你认为对但我们没想到的方案，不用担心"是不是最终拍板"。

## 一、我们是谁，已经做了什么（截至2026-09-18）

XY操盘系统是一套面向私域电商/自媒体从业者的Claude Code技能包（45个skill），核心资产是一个27,853条结构化知识原子的库（`atoms.jsonl`，每条一个具体判断/案例/原则，带type/topics/related字段）。

过去两天，我们给这个原子库做了一次完整的"本体论/FDE方法论"实操（不是纸上谈兵，是真代码真数据）：

1. **本体骨架**（`knowledge/ontology-schema.md`）：给27,853条原子定义了Class（8类type：definition/principle/method/case/anti-pattern/number/insight/risk）+ Relation（5种rel：supports/contradicts/example_of/prerequisite_of/refines）+ Action层（检索/写入/校验/迁移/路由5种可执行动作）+ 边界声明，`scripts/ontology-lint.py`校验0违规

2. **概念节点中间层**（`knowledge/concepts.jsonl`，设计文档`knowledge/concepts-schema.md`）：因为27,853条原子直接两两建关系是C(27853,2)≈3.9亿组合不现实，我们加了一层聚合节点——原子只挂到"概念节点"上当证据，节点之间才建关系。**现在这套已经覆盖全部13个topic，共309个概念节点**，每个节点有明确的证据原子链+摘要+节点间关系，累计23,812条原子完成了数据质量重新分类（发现原topics标注里有大量第三方通识商业内容被机械误标，独立建了"通用商业管理"topic承接）

3. **真实客户案例验证**：拿一个真实客户的交易系统（N+模块的真实生产代码库，不是demo）完整走了一遍本体建模六步法（定边界→抽实体→定类型→建层级→抽关系→验证），挖出了真实的历史生产事故模式、版本不对齐问题、被遗漏的核心实体——证明这套方法论在陌生复杂系统上真的能跑通，不是自娱自乐

4. **架构参考**：过程中读了腾讯WeKnora（开源RAG+Wiki框架，MIT license）的源码，照搬了几个具体设计决策（候选节点两遍提取、去重"宁可留重复不错合并"、入库时判断矛盾关系而非事后批量扫、ego-network检索），但**有一条被推翻了**：设想的"字符相似度两级漏斗"用真实数据校准后证明不可靠（召回率和过滤精度都不够），已经改用规则级前缀过滤，这个教训你应该知道，避免重复踩坑

## 二、已经拍板、不需要你重新论证的决策

- **付费产品不卖知识库，卖方法论工具**：客户拿到的不是一堆XY自己的私域运营知识，是我们验证过的"六步建模法+概念节点聚合方法+校验规则"，客户填入自己公司的数据，产出的是客户自己公司的本体
- **内容IP纪律**：第三方原创研究材料只能"重塑不照搬"（吸收逻辑、用自己的话重新表达，不用对方框架和措辞）；MIT等permissive license的真代码可以直接照搬具体实现（字段设计/算法/流程步骤），这两者是不同的风险类别，不要混为一谈
- **技术栈偏好**：现有全部工具是zero-dependency纯Python脚本（无框架、无数据库、无向量库），这不是"技术选型待定"，是已经跑通两天验证过的路线，除非你有极强理由，默认沿用这个思路而不是建议上一整套Go/Postgres/向量库这种重型架构

## 三、我们自己还没答案的核心设计问题（这是你要真正解决的）

### 问题1：产品的交付形态是什么？

三个候选，各有明显问题，需要你给出判断或第四个方案：
- **A. 独立Claude Code skill，客户自己在自己电脑上跑**：好处是可复制、边际成本低；问题是客户的Claude Code要能跑Python脚本、要理解怎么准备自己的数据喂进去，非技术客户可能用不起来，而且skill一旦交付出去，方法论细节（我们的prompt设计、判断规则）客户理论上都能看到，怎么防止被直接复制转卖？
- **B. 我们驻场/远程服务，用我们自己的工具跑客户数据**：好处是质量可控、天然防抄；问题是不可复制，本质还是卖时间不是卖产品，跟"FDE咨询"业务边界模糊，规模上不去
- **C. 混合模式**：具体怎么混，是"工具做80%+人工介入20%关键判断"，还是"免费工具自助+付费人工审核"，需要你设计出可执行的具体分工，不是空喊"混合"

### 问题2：这套方法论怎么泛化成"通用企业版"，而不是"XY私域版"？

我们验证过的六步法+概念节点方法目前是针对XY自己（私域电商知识）和一个客户（交易系统代码）两个具体领域跑通的。这两个领域差异很大（一个是知识文本库，一个是代码库），说明方法论本身有一定通用性，但：
- 具体的"候选节点提取标准""去重判断标准"这些prompt/规则，是不是需要针对客户所在行业做定制？定制这件事本身要不要工具化，还是每次人工介入？
- 客户自己的"topics/type分类体系"（我们是13个topics+8个type，客户公司的业务分类完全不同）要不要求客户按我们的模板削足适履，还是工具支持客户自定义分类体系？如果支持自定义，哪些部分是可配置的、哪些是方法论核心不能变的？

### 问题3："AI Native / 自我迭代"这个长期方向怎么落地？

XY的老板（后面简称"用户"）明确要求：这套东西最终要能自我迭代，但**迭代的驱动力必须来自客户真实使用后的反馈/案例积累，不是靠XY这边人工持续维护**。现有的概念节点设计（版本历史机制`concepts_revisions.jsonl`、入库时矛盾判断）只解决了"XY怎么维护自己的库"，完全没有设计"客户的引擎怎么吃客户自己的真实反馈自我进化"。这是一个几乎空白的设计问题，需要你从头想：客户用这个工具产生了新的业务判断/新的案例之后，这些东西怎么被系统识别、怎么判断该不该更新进客户自己的本体、要不要人工审核这个环节、多长时间迭代一次。

### 问题4：怎么防抄/护城河设计？

之前讨论过一个思路——"云端授权网关"：本地skill是薄客户端，真正的方法论逻辑（prompt/判断规则）放在服务端API，客户端只是调用，配license key验证。这个思路有一个明显张力还没解：**部分行业客户（金融/医疗/涉密行业）要求数据完全不出本地环境**，如果核心逻辑必须联网调用云端API，这类客户直接用不了。这个矛盾怎么解，需要你提出具体方案，不是回避这个问题。
