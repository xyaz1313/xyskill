# G7 · Action层能力 —— 设计文档

状态：已跟用户完成brainstorming对话确认，待用户复核本文档后进入实现计划。

## 一、要解决什么问题

`enterprise-engine`（私有仓库 `xyaz1313/xyskill-enterprise`）现有G0-G6闸门流程，产出的是客户业务的**结构化知识本体**（实体/类型/层级/关系），本质是只读的——FDE帮客户把业务结构梳理清楚，AI基于这套结构给判断建议，但不碰客户真实系统的数据写入。

用户明确要求：这条能力线要对标Palantir Foundry的"可执行业务本体"（Ontology + Action Type），能真正帮客户**执行**业务动作（审批订单、改状态），而不只是给建议。同时用户自己也指出：不同客户用的系统五花八门（企业微信/有赞/自研系统/传统ERP），不可能预先做一个"万能连接器"，真正连接客户系统的代码必须由驻场工程师现场针对客户实际系统编写——这一点在设计中作为硬约束保留。

## 二、范围（brainstorming阶段已用AskUserQuestion确认的4个决策）

| 决策点 | 选择 |
|---|---|
| v1做到什么程度 | 方法论 + 安全脚手架，不做预置连接器 |
| 开放给哪个服务档位 | 只开放给驻场档（`enterprise-engine`现有三档：自助/审核/驻场） |
| 和G0-G6的关系 | 新增G7，必须在G0-G6跑完（客户实体/关系模型已验证）之后才能开始 |
| 执行动作的审批门槛 | v1一律人工确认，不设自动执行例外 |

补充约束（用户在设计过程中追加，已吸收进本设计，不单独展开）：**G7的Rule检查在判断"能不能执行这个动作"时，必须现查客户系统当下的真实数据，不能只依据G0-G6建模时留下的静态快照判断**——理由：静态本体只回答"按规则应该怎样"，答不出"现在实际怎样"，用旧快照做执行判断（例如凭建模时的"客户信用良好"批一笔实际已逾期的额度）是真实的业务风险，不是理论风险。这条是G7内部的安全规则，不是独立子系统。

## 三、明确不做什么（划清界限，避免被理解为"XY要做一个企业执行平台"）

- 不做通用ERP/CRM连接器产品，不预置任何具体系统（企业微信/有赞等）的现成对接代码
- 不做自动化/自主执行——v1没有任何动作可以绕过人工确认
- 不做"实时上下文/事件时间线"能力（捕捉客户业务事件、支持按时间追溯"这个问题是什么时候开始的"）——这是brainstorming过程中用户从另一段材料引出的相关但独立的能力，范围明显大于G7（对只读诊断场景也有价值，不止Action执行场景用得上），决定作为**G7之后的独立后续设计**处理，不塞进本次spec，避免两个子系统混在一起导致都不聚焦
- 不承接客户数据——沿用已有原则，客户业务数据、生成的集成代码都只留在客户自己的机器上，不回传给XY

## 四、三个组件

### 1. `enterprise-engine/gates/g7-action-layer.md`（新增闸门文档）

跟现有G0-G6闸门文档同样的风格（checklist式，供FDE驻场时对照执行）。核心内容：把G0-G6产出的实体/关系模型转成一份**Action清单**，每条Action必须写清楚：

- 改的是哪个实体的哪个状态（对应G0-G6里已经定义好的Class/实体）
- 谁有资格触发这个动作（权限前置条件）
- 触发前必须满足什么条件才允许执行（Rule，且Rule必须查询客户系统当下真实数据，见二节补充约束）
- 执行后产生什么可观察的效果、是否可回滚

这套结构直接对应Palantir Action Type的设计纪律（Create/Modify/Delete Object + Rule），但用XY自己的语言表达，不引入Palantir的术语包装。

### 2. `enterprise-engine/scripts/action-scaffold/`（新增安全代码脚手架）

不是连接器，是一套**通用安全模式**的参考实现（Python，因为`enterprise-engine`现有代码全部zero-dependency纯Python，延续同一技术路线）：

- **Rule校验包装器**：执行真实写操作前，先跑权限检查+前置条件检查，任何一项不过直接拒绝，不静默降级
- **dry-run开关**：默认开启，只打印"将要执行的具体变更"，不真的调用客户系统的写接口
- **人工确认断点**：dry-run验证过、且Rule检查通过后，把具体变更内容（改哪个字段、从什么值改成什么值）完整展示出来，等待人显式确认（非空回车、非默认yes），才允许进入真实执行分支
- **本地审计日志**：每次真实执行（无论成功失败）追加写入本地日志文件，记录时间/触发人/变更内容/结果；日志只留在客户机器上

FDE现场把客户系统的真实API调用包在这套模式里面，而不是从零写安全逻辑、从零想"要不要加审批"。

### 3. `skills/xy-fde/SKILL.md` 新增边界说明

在现有"诚实边界"部分追加一条：客户问"能不能帮我们接ERP直接执行业务动作"时，标准回答需要包含三层意思——① 这是G7阶段的事，前提是G0-G6已经把业务结构梳理清楚；② 这不是"装个插件就通"，是驻场工程师针对客户实际系统的现场定制工程；③ 我们提供的是安全纪律和代码安全模式，不是一个能直接对接任意系统的成品连接器。不允许为了显得"什么都能做"而模糊这三层边界。

## 五、数据流

```
G0-G6产出（客户实体/关系模型，已验证）
    ↓
FDE识别哪些实体需要可执行Action，逐条按g7-action-layer.md清单写清楚Rule/权限/回滚方式
    ↓
FDE用action-scaffold的安全模式，包住客户系统的真实API调用，写出这次engagement专属的集成代码
    ↓
dry-run验证（只打印不执行）→ 确认逻辑符合预期
    ↓
真实执行：Rule现查客户系统当下数据 → 权限检查 → 人工确认断点（展示具体变更）→ 执行 → 写本地审计日志
```

## 六、验收标准（G7闸门"过关"的判定）

- 每个已定义的Action都能跑通dry-run，且dry-run输出的"将要变更的内容"人工核对无误
- 每个Action的Rule检查都能证明是查询的实时数据（不是G0-G6快照缓存）
- 没有任何代码路径能绕开人工确认断点直接触达客户系统的写接口
- 审计日志字段完整（时间/触发人/变更前后内容/结果），且验证过日志不会被静默跳过
